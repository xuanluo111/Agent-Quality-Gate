## 二、真缺口 backlog（按 价值 ÷ 成本 排序）

### G1 · 算法级确定性裁判（从鑫） — **订正：Jaccard 早已实现；现补齐记录式 P/R；真剩余=VRI**
- **来源**：从鑫《复杂问题抽象评测》§7（Jaccard/PV 冗余惩罚 + VRI 角色乱标）。
- **本条初稿写错了**：曾写“全库 `grep Jaccard`=0 命中、待实现”——实际只搜了英文词、没搜项目缩写 `jcv`。
- **已实现（勿重复造）**：`judge.py:1228 _compute_jcv` 就是标准 Jaccard（`∩/∪`），低于 `jcv_threshold`(0.6) 判 `JCV_Mismatch`；“冗余提取过多→Fail”也已被 Jaccard 覆盖（多余变量撑大并集→分数下降）。
- **本次已补（G1-lite，已完成）**：新增模块级纯函数 `compute_variable_pr` 从同一对集合拆出 **Precision（冗余反面）/ Recall（漏抽反面）**，经 `_finalize` 写入 `EvalResult.jcv_precision/jcv_recall`（**仅归因记录、不改判负**）；JCV 判负 evidence 与 `report.py` 展示“漏抽 vs 冗余”。属运行输出字段 → **不碰数据集、不切代**（epoch=数据集文件字节 SHA256 前 16，`dataset.py:93`）。
- **真剩余缺口（VRI）**：变量“名字对但角色/类型标错仍应判负”——现 `extracted_variables: List[str]`（`schema.py:307`）**根本没有角色/类型维度**（已核实 `variables.py` 只返回名字）。落地需新增 `expected 变量→角色` 字段 + 改抽取器/runner + 新用例 → **需切代**，与“保留已真实跑过的判负口径”冲突，故归入下个本就切代的批次顺带做。
- **工作量**：G1-lite 已完成；VRI 中（需切代）。

### G2 · 难度维度分层抽样（IRT-lite） — **P1，谨慎**
- **来源**：张辉帅《IRT 抽样》§2。
- **做什么**：现 `stratified_sample` 按 `category + severity`（`dataset.py:195`，method `stratified_category_severity`）分层；可显式引入 `difficulty`（Easy/Medium/Hard）维度，抽出最具代表性的黄金代理子集，用小样本逼近全量排名。
- **现状**：无独立 `difficulty` 字段（`severity` 是严重度、不是难度）。
- **⚠️ 关键代价**：**换抽样维度会让分层洗牌**，与上一代通过率不可直接比较——必须随真实批次自然切 `dataset_epoch`，且 README 已明确本项目**不做真 Item Response Theory**，只是"分层抽代理子集"的借喻，措辞别过度声明。
- **工作量**：低（schema 加字段 + 抽样加一维），但切代/验证成本不低。

### G3 · `Fail_Abstraction` 中间态断言 — **P1**
- **来源**：从鑫 §7（`00-四框架知识映射.md` 借鉴区已登记为未实现）。
- **做什么**：在 Trace 中途拦截——若 Agent 跳过变量识别/规划直接落到写代码/调工具，报 `Fail_Abstraction`。现框架只断言**终态**（`state_assertions`），无"中间步骤缺失"检测。
- **现状**：全库 `grep Fail_Abstraction` = 0 命中。
- **切代影响**：需新增 `fail_reason` 枚举 + 对应用例 → **需切代**。
- **工作量**：中（runner 中间态钩子 + schema 枚举 + 用例 + 门禁分支）。

### G4 · 真·MockUser 多轮施压驱动 — **P2**
- **来源**：张辉帅 §2。
- **做什么**：现多轮对抗是**把"第一轮/第二轮…"写死在单条 `input` 字符串里的静态场景**（见 `core_suite.jsonl` 工具与行动安全多轮用例），并非根据 Agent 上一轮回复**动态生成下一轮**。缺一个 turn-by-turn 的 MockUser 驱动层（正常问 → 身份伪造 → 威胁施压）。
- **价值**：真正测出"上下文已被建立后越权升级"的长程防御。
- **切代影响**：改 runner 执行模型，不动数据集本身可不切代；但新增用例结构可能触发切代。
- **工作量**：中高（改 `runner.py` 循环 + 新用例契约）。

### G5 · 动态评测权重（品味自适应） — **P2**
- **来源**：李鹏 §7。
- **做什么**：把各能力/风险维度的门禁权重做成可配置项（现为硬编码阈值），支持按场景自适应调权。
- **工作量**：低（`config.py` + `gate.py` 读配置），但要注意别把"放宽断言"当配置自由度。

### G6 · 单次执行**聚合**墙钟熔断 — **P2（小）、不切代、但真实数据下几乎不触发 → 归入下批次顺带做**
- **来源**：张辉帅 §3。
- **关键事实（结合实际）**：项目**已有超时**——`config.py:73 request_timeout=300`（`runner.py:199` 塞进 OpenAI SDK）封的是**单次 API 调用**，不是整条 case。`max_rounds=4` 下一条 case 理论最坏 ≈ 4×300 + 退避 ≈ **1200s+ 无人管**——所以 G6 是“整案聚合熔断”，不与现有重复。
- **真实耗时分布**（最近两批次 177 条全量的 `trace.latency_ms`）：慢模型 spark-x2.5-4b 中位 12.8s / p90 72.1s / p99 170.0s / **max 183.9s**（>120s 有 6 条）；快模型 ling-3.1-flash max 45.9s。**全量无一超 300s**。
- **⚠阈值口径（别再拍脑袋）**：**不能定 120s**——会误伤 4b 批次 6 条正常但慢的 case。建议取观测 max 的 2.5–3×、且明显低于理论堆叠：per-case 聚合 **480s** 作“跑飞护栏”（只抓循环失控，不碰正常长回答）。`request_timeout=300` 已封死单卡死→**G6 当前命中概率极低**，价值是兜底保险、非补漏判。
- **归因**：与 `Step/Token_Budget_Exceeded` 同款（stage=iteration、预算耗尽判负），因为它只抓“循环跑飞”、本就是稳定性问题而非能力问题。
- **节奏**：不单独做；随下次真实批次与 G3/G7/VRI 打包上（不切代、零额外窗口成本），且只有真批次跑起来才能验证阈值。**工作量**：低（config+1 参、schema+1 `is_time_exceeded`、runner 循环查墙钟、judge 加 `Time_Budget_Exceeded` 分支、report 展示）。

### G7 · Seed Mutation 种子变异造数据 — **P2**
- **来源**：潘亮铭 §3。
- **做什么**：不从零编用例，基于高危"种子"让模型变异（换话术、加伪装、编码混淆）扩充对抗集。现 `generate_cases.py` 有生成，但"种子定向变异"未成体系。
- **⚠️ 注意**：生成数据须过 `build_suite.py` 去重与 Schema 校验闭环（刘泽群 Coder-Checker 的思路），并遵守数据集构建去重规范。
- **切代影响**：批量加用例 → **需切代**。

### G8 · 多 Agent 链路被测 / `reflection_history` / `workflow_changes` — **P3（偏架构）**
- **来源**：王宏宁《情境学习与协作发现》§50-53、闫宇坤《PilotDeck》。
- **做什么**：从"单 Agent 节点"升级为"多 Agent 链路/工作流整体"被测；schema 增 `reflection_history`（自我反思轨迹）、`workflow_changes`（动态调整工作流历史），检"越补漏洞越大"与"多 Agent 幻觉传染"。
- **现状**：全库三者均 0 命中（`00-四框架知识映射.md` 借鉴区已登记）。
- **工作量**：高，属架构级演进，非小补丁——建议单独立项评估，不进近期 backlog。

## 四、落地节奏建议

1. **G1 已分阶段落地**：Jaccard 本体早已实现（JCV）；G1-lite（记录式 P/R 归因）本次已完成，不切代。剩下的只有 VRI。
2. **切代批次一次性打包**：G1-VRI、G3（Fail_Abstraction）、G7（种子变异）均需切代——别为单条枚举/字段单独切代，攒到同一批次一起做最经济。

5. **G8** 架构级，需要时单独立项，不混进常规批次。
